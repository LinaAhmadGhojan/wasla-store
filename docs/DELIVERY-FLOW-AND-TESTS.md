# تدفق التوصيل والتتبع — وصلة (Wasla)
**تاريخ:** 2026-09-07  
**الهدف:** فهم ماذا يحصل من الطلب حتى التسليم/الفشل، وكيف نختبره، وكيف يرتبط الموقع + الداشبورد.

> **واقع اليوم قبل البناء:** الموقع عنده طلبات بحالات بسيطة (`pending → confirmed → shipped → delivered`).  
> **ما كان موجود:** إسناد سائق، OTP، توقيع، صورة استلام، سبب فشل، تايملاين تتبع للزبون.  
> هذا الملف يصف التدفق الكامل المطلوب + سيناريوهات الاختبار. التنفيذ يبدأ بنفس المشروع.

---

## 1) الأطراف

| الطرف | أين يعمل | ماذا يفعل |
|------|----------|-----------|
| الزبون | الموقع / التطبيق | يطلب، يدفع، يتتبع، يدخل OTP عند الاستلام |
| الأدمن | الداشبورد | يؤكد الطلب، يسند سائق، يراقب الحالات |
| السائق/المندوب | تطبيق التوصيل (لاحقاً) / مؤقتاً من الأدمن | يستلم من المستودع، يوصل، يطلب OTP، يرفع توقيع/صورة، يعلّم نجاح أو فشل |
| النظام | Backend Laravel | يولّد OTP، يحفظ الأحداث، يمنع قفزات حالة غير قانونية |

---

## 2) حالات التوصيل (Delivery Status Machine)

```
pending
  → confirmed
    → preparing                 (تجهيز بالمستودع)
      → assigned                (إسناد سائق)
        → picked_up             (استلام من المستودع)
          → out_for_delivery    (في الطريق)
            → delivered         (نجاح + OTP + توقيع اختياري)
            → failed_delivery   (فشل محاولة)
              → out_for_delivery (إعادة محاولة)
              → returned         (مرتجع للمستودع)
              → cancelled
    → cancelled                 (قبل الشحن)
```

### ماذا يلزم عند كل انتقال؟

| من → إلى | مطلوب |
|----------|--------|
| confirmed → preparing | أدمن |
| preparing → assigned | اختيار سائق (`driver_id`) + توليد OTP (4–6 أرقام) |
| assigned → picked_up | سائق / أدمن |
| picked_up → out_for_delivery | سائق / أدمن |
| out_for_delivery → delivered | OTP صحيح من الزبون + (توقيع أو صورة إثبات اختياري حسب الإعداد) |
| out_for_delivery → failed_delivery | سبب فشل إلزامي |
| failed_delivery → out_for_delivery | إعادة جدولة |
| * → cancelled | سبب اختياري + قبل التسليم فقط |

---

## 3) التدفق السعيد (Happy Path)

1. الزبون يعمل Checkout → طلب `pending` + دفع  
2. الأدمن يؤكد الدفع (إن لزم) → `confirmed`  
3. الأدمن يبدأ التجهيز → `preparing`  
4. الأدمن يسند سائق → `assigned` + يظهر رقم تتبع + OTP يُرسل للزبون (واتساب/إشعار لاحقاً؛ حالياً يظهر في الأدمن + صفحة التتبع للزبون المسجّل)  
5. السائق يستلم من المستودع → `picked_up`  
6. السائق يخرج → `out_for_delivery` — الزبون يشوف «السائق في الطريق»  
7. عند الباب: الزبون يعطي OTP → السائق يدخل OTP  
8. توقيع إلكتروني أو صورة استلام  
9. الحالة `delivered` + `delivered_at` + حدث في التايملاين

## 4) مسارات الفشل الشائعة

| # | السيناريو | النتيجة |
|---|-----------|---------|
| F1 | الزبون غير موجود | `failed_delivery` سبب: customer_absent |
| F2 | رفض الاستلام | `failed_delivery` سبب: customer_refused |
| F3 | عنوان خاطئ | `failed_delivery` سبب: wrong_address |
| F4 | OTP غلط 3 مرات | قفل مؤقت + تنبيه أدمن |
| F5 | دفع كاش والزبون ما معه كامل المبلغ | `failed_delivery` سبب: cash_issue (لـ COD) |
| F6 | إلغاء قبل الشحن | `cancelled` |
| F7 | مرتجع بعد فشلين | `returned` |
| F8 | تلف بالطرود عند التسليم | `failed_delivery` سبب: damaged + صورة |

## 5) الربط: موقع ↔ داشبورد ↔ (تطبيق سائق لاحقاً)

```
[Checkout موقع]
      │
      ▼
[orders + payments] ──► [Admin: طلبات المتجر]
      │                        │
      │                        ├─ تأكيد دفع
      │                        ├─ تغيير حالة / إسناد سائق
      │                        └─ عرض OTP / التوقيع / الأحداث
      │
      ▼
[صفحة تتبّع الطلب /orders/{id}/track]
      │
      ├─ تايملاين الأحداث
      ├─ أين صار الطلب الآن
      └─ إدخال OTP عند الاستلام (اختياري من طرف الزبون للتأكيد)
      
[API سائق — لاحقاً]
  POST /api/driver/orders/{id}/status
  POST /api/driver/orders/{id}/verify-otp
  POST /api/driver/orders/{id}/proof  (signature / photo)
```

طلبات الشراء الخارجي (`purchase_requests`) تبقى منفصلة حتى `received` بالمستودع؛ بعدها يمكن إنشاء/ربط طلب توصيل محلي لنفس الزبون (مرحلة لاحقة).

## 6) سيناريوهات اختبار (Checklist)

### أ) إنشاء الطلب والدفع (1–15)
1. طلب كاش عند الاستلام  
2. طلب سيرياتيل كاش + رفع إيصال  
3. طلب MTN كاش  
4. طلب شام كاش  
5. طلب تحويل بنكي  
6. طلب رصيد متجر  
7. سلة منتجات محلية فقط  
8. سلة مختلطة (محلي + خارجي) — سلوك متوقع: طلب محلي + PR منفصل  
9. ضيف يضيف للسلة ثم يسجّل عند الدفع  
10. عنوان ناقص → رفض  
11. عنوان كامل → نجاح  
12. كمية أكبر من المخزون → رفض/تنبيه  
13. إلغاء قبل التأكيد  
14. تأكيد دفع من الأدمن  
15. رفض إيصال دفع من الأدمن  

### ب) التجهيز والإسناد (16–30)
16. confirmed بدون سائق  
17. preparing  
18. إسناد سائق موجود  
19. إسناد سائق غير موجود → خطأ  
20. تغيير السائق بعد الإسناد  
21. توليد OTP تلقائي عند الإسناد  
22. إعادة توليد OTP  
23. رقم تتبع يظهر للزبون  
24. محاولة إسناد بعد delivered → مرفوض  
25. إلغاء بعد assigned  
26. إلغاء بعد out_for_delivery → سياسة واضحة  
27. أدمن يشوف قائمة الطلبات حسب الحالة  
28. فلتر حسب السائق  
29. فلتر حسب الدفع  
30. طباعة/نسخ رقم التتبع  

### ج) الطريق والتتبع (31–50)
31. picked_up يسجّل حدث  
32. out_for_delivery يسجّل حدث  
33. الزبون يفتح صفحة التتبع ويرى التسلسل  
34. زبون آخر ما يقدر يفتح طلب مش إله  
35. ضيف بروابط بدون توكن → مرفوض  
36. تايملاين بالترتيب الزمني  
37. رسالة «وين صار» تطابق الحالة  
38. تحديث الصفحة يظهر آخر حدث  
39. لا قفز من pending إلى delivered مباشرة (إلا أدمن بصلاحية override إن وُجدت)  
40. shipped القديم القديم مع out_for_delivery للتوافق  
41–50. اختبار كل انتقال قانوني / غير قانوني في الآلة  

### د) OTP (51–65)
51. OTP صحيح → نجاح  
52. OTP خاطئ → خطأ  
53. OTP فارغ → خطأ  
54. OTP منتهي (إن فعّلنا expiry)  
55. إعادة إرسال/إعادة توليد  
56. عرض OTP للأدمن فقط أو للزبون المسجّل حسب السياسة  
57. السائق ما يشوف OTP في الـ API (يدخله فقط)  
58. بعد delivered ما عاد يُقبل OTP  
59. محاولات فاشلة متعددة  
60. OTP بعد failed_delivery ثم إعادة محاولة  
61–65. أطوال OTP (4/6) وحروف ممنوعة  

### هـ) التوقيع والإثبات (66–80)
66. رفع توقيع صورة PNG/JPG  
67. رفع صورة استلام  
68. ملف كبير جداً → رفض  
69. نوع ملف غير مسموح → رفض  
70. delivered بدون توقيع إذا الإعداد اختياري  
71. delivered بدون توقيع إذا الإعداد إلزامي → رفض  
72. عرض التوقيع في الأدمن  
73. عرض الإثبات في صفحة التتبع (مصغّر)  
74. حذف/استبدال إثبات قبل الإغلاق  
75. إثبات بعد failed لا يغيّر الحالة لوحده  
76–80. صلاحيات من يشوف الملفات  

### و) الفشل والمرتجع (81–95)
81. فشل: الزبون غائب  
82. فشل: رفض  
83. فشل: عنوان خاطئ  
84. فشل بدون سبب → مرفوض  
85. إعادة خروج بعد فشل  
86. مرتجع للمستودع  
87. إلغاء بعد مرتجع  
88. كاش COD: تحصيل عند النجاح فقط  
89. كاش COD: فشل بدون تحصيل  
90. إشعار/سجل حدث لكل فشل  
91–95. حالتان فاشلتان ثم مرتجع تلقائي (قاعدة عمل)  

### ز) الداشبورد والموقع معاً (96–110)
96. تغيير حالة من الأدمن يظهر فوراً بالتتبع  
97. OTP من الأدمن (محاكاة سائق) يكمّل التسليم  
98. رابط «تتبّع الوصلة» بعد نجاح الطلب  
99. قائمة طلباتي للمتجر المحلي (مش بس PR)  
100. سائق تجريبي `driver@wasla.test` يظهر بقائمة الإسناد  
101. طلب بدون عنوان شحن  
102. طلب ملغي ما يظهر كـ «في الطريق»  
103. أكثر من طلب لنفس الزبون  
104. نفس السائق على طلبين  
105. بحث برقم التتبع  
106. صلاحية أدمن فقط لتغيير الحالة  
107. API show order يرجع delivery timeline  
108. تخزين الملفات على disk العام/خاص حسب السياسة  
109. وقت delivered_at يُملأ تلقائياً  
110. canceled_at يُملأ عند الإلغاء

## 7) سياسة مقترحة للـ OTP والتوقيع

| البند | اقتراح افتراضي |
|------|----------------|
| طول OTP | 6 أرقام |
| صلاحية OTP | حتى التسليم أو إعادة التوليد |
| من يرى OTP | الزبون (حسابه) + الأدمن — السائق يُدخل ولا يجلب |
| التوقيع | اختياري في المرحلة 1، إلزامي لاحقاً |
| صورة إثبات | اختيارية |
| سبب الفشل | إلزامي |

## 8) ماذا ننفّذ أولاً (اليوم)

1. حقول التوصيل + جدول أحداث التتبع  
2. آلة الحالات + توليد/تحقق OTP  
3. داشبورد: إسناد سائق + تحديث مراحل + رفع إثبات + تسجيل فشل  
4. موقع: صفحة تتبّع طلب بتايملاين  
5. API للتتبع والتحقق  

**خارج نطاق «اليوم» الحقيقي:** تطبيق سائق Flutter كامل، GPS حي، واتساب OTP تلقائي، ربط PR→توصيل آلي لكل الحالات، إنهاء كل شاشات ui2.

---

## 9) كيف تجربين يدوياً بعد التنفيذ

1. اطلبي طلب من الموقع  
2. من الأدمن: أكّدي الدفع → confirmed → preparing → أسندي السائق  
3. انسخي رقم التتبع / افتحي `/orders/{id}/track`  
4. من الأدمن: picked_up → out_for_delivery  
5. أدخلي OTP → ارفعي توقيع → delivered  
6. كرّري طلب ثاني وجرّبي failed_delivery بسبب «الزبون غائب» ثم إعادة محاولة
